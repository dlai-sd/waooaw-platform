Claim ID:        C-098
Type:            OBLIGATION + PLATFORM_INTEGRITY
Statement:       The WAOOAW platform software architecture must enforce the
                 following structural invariants computationally after every sprint
                 execution, before a PR is opened:

                 (1) Layer isolation: no src/billing-engine/ file may import from
                     src/ai-runtime/ or src/bp/ (cross-layer dependency prohibition).
                     The billing engine is a downstream consumer of platform services;
                     it must never import from the AI Runtime or Business Platform
                     layers. Cross-layer imports introduce hidden coupling that
                     prevents independent deployment and violates the Constitutional
                     Engine's service boundary enforcement.

                 (2) No wildcard imports in service files: files named service.py,
                     models.py, router.py, or bundle_engine.py must not contain
                     "from X import *". Wildcard imports make dependencies opaque
                     to the LLM, cause name collision bugs that are difficult to
                     detect in review, and violate C-059 (Traceability — every
                     symbol must be traceable to its origin).

                 (3) Test file completeness: every billing-engine sub-package that
                     contains a service.py must have a corresponding test file at
                     tests/billing-engine/test_{package_name}.py. A service without
                     tests is not constitutionally complete regardless of how many
                     example-based or property-based assertions it has.

                 (4) Layered structure: every sub-package with a service.py must
                     also have a models.py (Pydantic models defined separately from
                     service logic). This enforces separation of data contracts from
                     business logic — a structure that enables mocking in tests.

                 Enforcement: scripts/check_arch_fitness.py runs post-execution,
                 after the LLM has written code and before the PR is created. Non-
                 blocking in the current implementation (violations are logged, not
                 fatal) to allow iterative improvement without blocking legitimate
                 sprint output. Violations are escalated to Founder review via the
                 Sprint Dashboard report.

                 Future: when the platform reaches G4 CLEAR, check_arch_fitness.py
                 violations become blocking (increments FAILURES). This is announced
                 in advance via IB entry.
